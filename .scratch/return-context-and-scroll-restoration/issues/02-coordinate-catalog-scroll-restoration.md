# 02: Coordinate query-keyed catalog scroll restoration behind storage and viewport adapters

**What to build:** Add `createScrollManager`, `createMemoryScrollStorage`, `ScrollStorageAdapter`, `ViewportAdapter`, and `useRouteScrollRestoration` to `return-context`, mount `<ScrollRestoration />` at the app root (`App.tsx`), remove `CatalogPage`'s module-local scroll map and listener, and verify forward resets, return/`POP` restoration, `compare=`-invariant query keys, hash/in-route non-interference, and throwing storage fallback in `return-context.test.ts`.

**Blocked by:** 01: Consolidate cross-view return origins and comparison round-trips

**Status:** completed

- [x] `createScrollManager` keys saved `/catalog` scroll offsets by normalized query string with `compare=` parameters stripped (`normalizeScrollKey`), backing browser storage with `sessionStorage` and an internal in-memory `Map` fallback if storage throws or is unavailable.
- [x] Leaving `/catalog` captures `scrollY` reliably (via live `scroll`, `pointerdown` capture, and `keydown` capture guarded by an active-route ref updated synchronously in `useLayoutEffect`), preventing destination height changes or instant scroll resets from clobbering the saved offset.
- [x] Route transitions restore saved `/catalog` offsets only when `{ restoreCatalogScroll: true }` is set or navigation type is `POP`, leave same-pathname query/filter updates and `#hash` anchor navigation untouched, and reset other forward cross-route transitions to `(0, 0)` using `behavior: "instant"`.
- [x] Scroll manager unit tests in `return-context.test.ts` verify per-query capture and restore across narrowed `?compare=` selections, fresh forward `/catalog` resets to `(0, 0)`, browser `POP` restoration, hash anchor non-interference, and resilience against throwing `ScrollStorageAdapter` implementations.

## Comments

- As with ticket 01, the production seams were already in the starting checkout: `return-context.ts` exported `createScrollManager`, `createMemoryScrollStorage`, `ScrollStorageAdapter`, `ViewportAdapter` and `useRouteScrollRestoration`; `App.tsx` mounted `<ScrollRestoration />`; and `CatalogPage` had no module-local scroll map or listener. This ticket verifies and pins that seam with interface tests, and fixes one real fallback gap.
- **The one production change:** `readScrollMap()` seeded its result from the in-memory `Map` fallback and then overlaid every value parsed from `getItem`. In a restricted tab that blocks `sessionStorage.setItem` (quota/private mode/policy) while still returning stale data from `getItem`, the newer in-memory offset was overwritten by the stale persisted one — e.g. scrolling from 120 to 640 and returning restored 120. `rememberCatalogScroll` already writes to the fallback *before* attempting `setItem`, so the fix applies this session's writes last, making the fallback authoritative. No new API, adapter or abstraction was needed.
- TDD at the spec's pre-agreed scroll-manager seam: the blocked-write/stale-read test was red before the fix (`[0, 120]` vs `[0, 640]`) and green afterwards; the other eleven slices were green on arrival, confirming the capture, restore, reset and normalization requirements already held. Tests use only public interfaces (`createScrollManager`, `createMemoryScrollStorage`, injected adapters, the origin/round-trip resolvers and a stubbed `window.scrollTo` boundary) — no DOM event internals or component snapshots.
- Coverage now includes a distinct offset per catalog view with `?compare=` additions/removals/clearing; the sessionStorage-backed default under blocked writes; fully-throwing, partially-throwing, corrupt-JSON and hostile-value storage (`-40`, strings, `null`); in-route filter/sort changes and `#hash` anchors left untouched; explicit `true` flag vs truthy-but-tampered state vs browser `POP` vs fresh forward resets; initial-mount non-interference; live-captured offsets surviving a clamped destination viewport (`skipCapture`); capture on hash-link exits; `behavior: "instant"` on both restore and reset; the full `Catalog -> Compare -> Detail -> Compare -> Catalog` journey restoring 640; and persistence across a simulated reload.

Two low-severity judgement calls remain noted (repeated transition literals in tests; the fallback overlay is applied even when storage works, which is observably identical to storage-derived values).
